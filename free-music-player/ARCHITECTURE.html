Operational Architecture — System Analysis & Data Flow Documentation

1. High-Level System Architecture Overview

The app follows the standard Electron two-process model: a Main Process (Node.js) that owns the SQLite database, file system, and network resolution, and a Renderer Process (Chromium) that runs React, Zustand stores, and the audio playback engine. Communication happens exclusively through IPC via ipcRenderer.invoke / ipcMain.handle behind a typed TypeScript wrapper.

🔵 Main Process

Node.js runtime. Owns all I/O: SQLite database, file system (downloads, cache), network (yt-dlp, YouTube Music API). Runs the HTTP proxy server for audio streaming. Handles all IPC requests from the renderer.

🟢 Renderer Process

Chromium browser context. Runs React, Zustand stores, and the engine layer. The AudioPlayer component owns two HTMLAudioElements and communicates with the MediaResolver's HTTP proxy for audio data. All database access goes through IPC.

🔍 Architectural Analysis: Process Boundary

The clean process boundary is this app's strongest architectural property. Every database read/write, every network request, every file system operation goes through typed IPC channels. This means the renderer could theoretically be swapped for a web frontend — the entire "backend" is already abstracted behind an IPC contract. Potential concern: the IPC bridge is the bottleneck for any operation that requires many round-trips (e.g., resolving 50 tracks at once). The app mitigates this with batch operations (verify) and background prefetching.

2. State Architecture Zustand

Three Zustand stores manage all application state. The engine layer (queueEngine, playbackController) is the source of truth for playback state — the Zustand stores are mirrors synced via syncFromEngine() after every mutation. This prevents React from being the single source of truth for time-sensitive playback state.

playerStore

currentTrack · isPlaying · progress · duration · volume · isMuted · isLoading · isShuffle · repeatMode · queue · queueIndex · queueHistory

Mirrored from queueEngine + playbackController via syncFromEngine(). Session persists via debounced save (1s).

libraryStore

tracks[] · favorites[] · recentlyPlayed[] · playlists[] · searchQuery · sortBy · sortOrder

Populated via IPC reads from SQLite. Optimistic updates on toggleFavorite — flips locally first, then fires IPC. Reverts on failure.

uiStore

currentPage · theme · modalOpen · toasts · isQueueOpen · isLyricsOpen · selectedPlaylistId · libraryTab

Pure presentation state. No engines, no persistence. Drives page routing (currentPage → page map in App.tsx).

🔄 Sync Pattern

engine mutation → syncFromEngine() → Zustand set() → React re-render → debouncedSave() → IPC → SQLite

The 1-second debounce on session saves prevents write storms during rapid queue operations (drag-reorder, skip, shuffle).

3. Audio Playback Pipeline Critical Path

This is the most latency-sensitive path in the app. From click to audio, the track goes through 5 layers — store → engine → AudioPlayer → MediaResolver → YouTube CDN.

Step-by-Step: Click → Audio

  1. 1 playerStore.playTrack(track) — sets queue, triggers playbackController, records play, persists history
  2. 2 playbackController.play(track) — emits trackChange, play, loading, duration events
  3. 3 AudioPlayer — picks up currentTrack change via useEffect
  4. 4 prefetchEngine.getSource(videoId) — check in-memory cache (populated by background prefetch)
  5. 5 ipc.stream.resolve(videoId) — main process resolves actual YouTube audio URL via yt-dlp
  6. 6 MediaResolver.tryResolve() — 4-tier cache check (memory → SQLite → verified → yt-dlp fetch)
  7. 7 Set audio element src — http://127.0.0.1:<port>/stream/<videoId>
  8. 8 HTTP proxy streaming — MediaResolver proxies net.request → YouTube CDN, pipes back to HTMLAudioElement
  9. 9 100ms progress poller — drives UI progress bar, triggers adaptive prefetch, updates audioBridge

Dual-Buffer Gapless Playback

Element A (Active)

Currently playing audio. 100ms poller reads currentTime, duration. Emits progress to playbackController.

Element B (Standby)

Preloads next track's source in background. When track changes, if readyState ≥ 3 (HAVE_FUTURE_DATA): instant gapless swap. Otherwise: normal load fallback.

⚠️ Circuit Breaker

Tracks errors in a 10-second sliding window. If >3 errors occur, auto-advance is disabled to prevent infinite error loops (e.g., when all queued tracks are unavailable).

🔍 Architectural Analysis: Audio Pipeline

Strengths: The local HTTP proxy is an elegant solution to Electron's streaming limitations. Using net.request (Chromium's network stack) instead of Node's http avoids CORS issues and correctly handles YouTube's CDN redirects. The dual-buffer architecture is a pragmatic approach to gapless playback without Web Audio API complexity.

Weaknesses: Two full HTMLAudioElement instances consume ~30-50MB each. The 100ms polling interval means the UI is always 100ms behind actual audio position. There's no AudioContext or Web Audio API — meaning no visualizer support, no cross-fading, no real-time audio processing. The proxy also introduces a serialization hop (HTTP) for every byte of audio — negligible for streaming but not ideal.

Recommendation: For a future v2, consider Media Source Extensions (MSE) with MediaSource API for true gapless, or Web Audio API for visualization and effects. The dual-buffer approach is a good intermediate solution.

4. Engine Layer Singletons

queueEngine

Pure in-memory queue state machine. setQueue · next · previous · add · playNext · remove · reorder · shuffle · setRepeatMode. Handles dedup, repeat modes (off/all/one), and Fisher-Yates shuffle.

playbackController

Event-driven state machine. Emits trackChange, play, pause, progress, duration, volume, loading, error. Subscribers: syncFromEngine, audioBridge, recommendationEngine.

prefetchEngine

Background MediaSource resolver. Pre-resolves next N tracks (adaptive: 5 burst, then 3 more at 45s remaining). Max 4 concurrent resolves. Cache: Map<videoId, MediaSource>.

queryEngine

Search with 2-layer cache (55-min TTL in-memory, 5-min TTL in main). 150ms debounce. AbortController for stale requests. Fire-and-forget background verification via yt-dlp.

recommendationEngine

Local listening history (100-entry). Top 3 artists → search YouTube → filter heard/heavily-skipped. Skip counter: ≥3 skips = excluded.

🔍 Architectural Analysis: Engine Pattern

The engine layer is the most architecturally sound part of the app. Engines are pure singletons with no React dependency, making them testable and portable. The separation between queueEngine (state machine) and playbackController (event emitter) follows command-query separation. The syncFromEngine bridge is a clean adapter pattern between the engine layer and React's render cycle.

Potential improvement: Engines currently live in the renderer process. For a high-performance architecture, they could be moved to the main process or a worker thread, communicating via IPC. This would keep the renderer thread free for UI work during heavy queue operations. However, this would add IPC latency to every playback operation, which is a non-trivial trade-off.

🔍 Architectural Analysis: IPC Surface Area

70+ channels is a large but well-organized surface area. The namespaced pattern (library:*, search:*) is clean and discoverable. Every channel is wrapped in a typed TypeScript function in src/utils/ipc.ts, so callers never deal with raw ipcRenderer.invoke strings.

Potential concern: There's no IPC timeout or retry logic. If a yt-dlp subprocess hangs (e.g., rate-limited by YouTube), the IPC call could block indefinitely. The app mitigates this somewhat with AbortController in search, but stream resolution lacks a timeout. Adding timeout handling to ipc.ts would improve robustness.

9. Key Architectural Decisions & Analysis

1. Local HTTP Proxy for Audio (instead of protocol.handle or direct streaming)

Why: Electron's protocol.handle has issues with ReadableStream serialization for large audio streams. The local proxy uses Chromium's net.request which correctly handles YouTube CDN redirects, Range requests, and streaming.

2. Dual-Process Engine Architecture

Why: Engines are pure TypeScript singletons (no React dependency) with Zustand as the mirror layer. This decouples business logic from the render cycle, making engines testable and keeping UI rendering predictable.

3. yt-dlp as Universal Media Resolver

Why: yt-dlp handles YouTube's ever-changing streaming protocols (DASH, of, etc.), extracts actual audio URLs, and provides format metadata. Building equivalent functionality in-house would be impractical.

4. SQLite for Everything (better-sqlite3)

Why: Synchronous SQLite avoids callback complexity for IPC handlers. No ORM — raw SQL queries keep performance predictable. A single free-music-player.db file stores tracks, playlists, queue, session, settings, and caches.

5. Dual-Buffer Gapless (not Web Audio API)

Why: Two HTMLAudioElements is the simplest approach to gapless playback. Web Audio API would require manually decoding audio buffers (memory-intensive) and implementing a streaming pipeline (complex). Trade-off: no audio visualization capability.

6. Optimistic Updates with Revert

Why: toggleFavorite flips the UI state instantly, then fires the IPC. If the IPC fails, the store reverts. This makes the UI feel instant while maintaining data integrity.

7. Debounced Session Persistence

Why: Queue operations (drag-reorder, skip, shuffle) can fire dozens of mutations in seconds. A 1-second debounce on SQLite writes prevents write storms while ensuring the final state is always saved.

8. Trust Score + Duration Mode for Search Ranking

Why: YouTube Music returns many results for the same song (official, lyric video, live, cover). Trust scoring (+100 for Topic channel, -1000 for live) combined with duration mode filtering (statistical mode of passing durations) selects the most likely "official" version.

9. Background Verification Pipeline

Why: Search results appear immediately (from ytmusic-api), then yt-dlp --dump-json runs in background (concurrency=3) to populate the verification cache before the user clicks play. This splits the UX latency from the verification latency.

10. Circuit Breaker on Audio Errors

Why: When multiple queued tracks are unavailable (private/deleted/blocked), auto-advancing through them creates an error loop. The circuit breaker (3 failures in 10s) stops auto-advance and lets the user manually intervene.

10. Vulnerabilities & Recommendations

🔴 No IPC Timeout

Stream resolution can hang indefinitely if yt-dlp is rate-limited. Add configurable timeouts to all IPC calls, with fallback behavior (skip track, show error toast).

🔴 No Service Worker

Offline support is limited to downloaded tracks. A service worker with a Cache-First strategy for search results and resolved streams would make the app feel instant even without network.

🟡 No Web Audio API

HTMLAudioElement limits prevent audio visualization, cross-fading, and EQ. Consider optional Web Audio API integration for the full-player view.

🟡 Memory: Two Audio Elements

Two HTMLAudioElements means ~60-100MB baseline memory just for audio playback. Consider lazy-loading the standby element only when there's a next track.

🟡 Engine Layer in Renderer

Engines run in the Chromium renderer process. Heavy queue operations (large shuffle) could block UI rendering. Moving engines to a Web Worker or main process would free the UI thread.

🔵 Exportable IPC Contract

The typed IPC wrapper (src/utils/ipc.ts) is already a clean API surface. This could be extracted into an NPM package or used to build a web-compatible backend.
